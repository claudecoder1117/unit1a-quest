## What was built

### `site/js/gen/figxlines.js` — `T-fig-xlines-L`, `T-fig-xlines-Q`
Two lines through one point, optionally a third ray with a right-angle square. Three frames, all reachable:

* `right` — rays `d 0° · c γ° · b 90° · a 180° · e (180+γ)°`, mark on `∠b v a` or `∠b v d`;
  labels on `∠b v c` and `∠a v e`; equation `E1 + E2 = 90`; asks `m∠c v d` (vertical) and `m∠d v e` (linear pair).
  This is `ang-10`'s exact shape.
* `linearpair` — 4 rays; labels on `∠a v c` and `∠c v d`; equation `E1 + E2 = 180`.
* `vertical` — 4 rays; labels on the vertical pair; equation `E1 = E2` (`mustMention` is then the label's
  own constant, so `x = 4` cannot pass the structural guard).

Answer-backward: the roots come first (`-Q` draws two from `{−1/2, −2, 1/2, 2, 3…9}`, at most one half so the
coefficients stay integral; `-L` draws one integer in `[−12, 25]`), then `k(x)`, then `E1 = mx + n`, then
`E2 = K − E1 + k` (or `E1 + k` for the vertical frame). **Both-valid vs one-invalid is a coin flip** on `-Q`
(the same rule S2 sets for `T-cs-quad`): an invalid root is one that drives a labelled measure to ≤ 0 or ≥ 180,
and it is rejected with `negative-angle` / `zero-angle` / `angle-over-180`. With one surviving root the `cases`
tab is replaced by a plain `multi` (a one-row case table is not a case table).
About 30 % of items print a label unsimplified (`84 − x`, `2x² + 3 − 4x`) — S2's "sometimes presented
unsimplified"; the `equation` grader canonicalises, so every spelling still grades.

### `site/js/gen/figsystem.js` — `T-fig-system`
`doc-07`'s figure: two lines, letters hidden, the four angles addressed by the position aliases
`UL / UR / LR / LL` (so `multi` fields carry `wedge:'UL'`). `x, y ∈ [−12, 12]`, integer coefficients, three of
the four angles labelled `ax + by + c` (which one is blank is drawn), the vertical equation and the linear-pair
equation independent (`det ≠ 0`, checked, and the solution re-derived and compared to `(x, y)`).
The `equation` part is the two-equation `system` form (`canonical: null`, `vars: ['x','y']`, `mustMention:[180]`)
plus a `text` field so the contract's `answerFor()` can round-trip it.

### `site/js/gen/figbisect.js` — `T-fig-bisect-L`, `T-fig-bisect-Q`
Three rays; the middle one splits the whole angle. **The verdict is chosen first** and the expressions are built
to match; a NO always differs by ≥ 4°. The drawn split is *deliberately* never the true one (always 6–16 % off
centre), so the picture can never give the answer away — the chip is automatic (`notToScale`).

`-L` is one Proof Strip in `doc-05`'s exact slot order (`pick → num → multi → verdict → chips`), with the two
wrong set-ups (`halves equal` = `assumed-bisects`, `sum = 180` = `linear-pair-set-equal`) as the pick's
distractors and one required / two forbidden chips.

`-Q` has two integer roots and one case per root. **All of yes/yes, yes/no and no/no occur.** The yes/yes case
needed care: `h1 − h2` is monic, so with a *linear* whole-angle expression a yes/yes item collapses into
`W ≡ 2·h2` — "it bisects for every x", a tautology. Those items therefore give `W` its own `x²` term
(`lead ≠ 1`), which keeps both roots bisecting while the equation stays a real quadratic. The
`assumed-bisects` misconception is omitted on yes/yes items, where setting the halves equal *is* a valid route.

### `site/js/gen/segmid.js` — `T-seg-mid`
`ang-04`: isosceles triangle, both legs' midpoints joined, so all four half-legs are equal. Labels `am + b`
and `m² + c` on halves of *different* legs, `n + k` on the other half of the first leg, a number on the base,
one half unlabelled. Roots `r1 > 0 > r2` with `b < a·|r2|`, so `r2` makes the printed length negative and the
`reject` reason really is `negative-length` (exactly one positive root, S2).

### `site/js/gen/figpairs.js` — `T-fig-pairs`
`ang-wu-*`: name N pairs with a relation. Three fan shapes — `lines` (2 lines), `perp` (2 lines + a
perpendicular ray = F1, the only shape with complementary pairs) and `ray` (2 lines + a generic extra ray).
Measures come from `GENERIC_ANGLE_SET` `{23, 29, 41, 47, 71, 79}` (+ 90); every candidate goes through
`accidentalSums(model)` — the enumeration gate — and is re-rolled if the drawing produces a 90°/180° sum the
structure does not justify. Letters shuffled (never I or O), rotation in 15° steps, optional mirror. Asked
relations: supplementary (2 or 3), linear pair (2), vertical (1 or 2), adjacent (3), non-adjacent (2),
complementary (1). The `pairs` part carries `figure: <the fan spec>` so it grades with no extra wiring.

### Figure quality gates (every template)
Each candidate figure is resolved and rejected unless **all** of:
`validate(model) === []` · `accidentalSums(model) === []` (fans) · `lint(model, {widthPx: 343}) === []`
(343 px = a 375 px phone minus the 16 px gutters — no clipped label, no overlap, every wedge ≥ 44 px) ·
`figureIsTidy(model)` — every expression label `fits` and sits at radius ≤ 124 (128 for `T-fig-system`), and
every fan ray is ≥ 108 units (96 for `T-fig-system`, whose letters are hidden). The last gate is this ticket's
own: the shipped figures sit at label radius ≤ 122 (`doc-07`) and ray length ≥ 122 (`F1`), and without it
about a quarter of variants pushed a long label so far out of a narrow wedge that it read as floating free.

Generated fans also get computed `labelOffsets.point`: `svg.js`'s default puts a ray letter straight past the
arrow tip, i.e. **on** the stroke (the hand-modeled figures dodge this by hand). Each letter is nudged along
its ray and then perpendicular, to the side away from the other rays.

## Exported API

Every module exports the same three things (plus its own helpers):

```js
// site/js/gen/figxlines.js
export const TEMPLATE_VERSION = 1;
export function drawXlinesL(rng) → draft|null       // one draw for the contract's re-roll loop
export function drawXlinesQ(rng) → draft|null
export function verifyFigure(item) → string[]       // the template's `verify` (figure re-checked)
export const genXlinesL = makeGen('T-fig-xlines-L', drawXlinesL, {…})   // gen(seed, params) → item
export const genXlinesQ = makeGen('T-fig-xlines-Q', drawXlinesQ, {…})
export default { genXlinesL, genXlinesQ, TEMPLATE_VERSION };

// figsystem.js   drawFigSystem · verifyFigure · genFigSystem
// figbisect.js   drawBisectL · drawBisectQ · verifyFigure · genBisectL · genBisectQ
// segmid.js      drawSegMid · verifyFigure · genSegMid
// figpairs.js    drawFigPairs · verifyFigure · genFigPairs
```

`gen(seed, params)` is T07a's contract: `gen.version`, `gen.exemplar()`, `gen.check(item)` all work.
Use the registry rather than the modules:

```js
import { generate, getTemplate, templatesForCard, modelOf } from '../data/templates.js';
const item = generate('T-fig-xlines-Q', 'a91f2c');     // byte-identical for the same seed
```

### The item a figure template returns (on top of the contract's fields)

```js
{
  id: 'T-fig-xlines-Q#a91f2c', template, templateVersion, seed, seedKey, attempt,
  params: {…},                       // everything needed to re-read the item (frame, roots, letters, measures…)
  stem, prompt,                      // the same string; `stem` is the name the card data uses
  note?: string,
  answer: 'x = 3, m∠CFD = 9° …',     // DISPLAY string (the contract requires a non-empty string)
  answerData: {…},                   // the structured answer (roots, rows, measures) for screens and tests
  figure: {                          // null on a non-figure template
    id: 'G-xlines-…',                // unique, prefixed `G-`; nothing here is in data/figures.js
    spec: {kind:'fan'|'poly', …},    // a COMPLETE figure object (S6 figure schema), ready to render
    rename: {}, labels: […], notToScale: true,
  },
  parts: [...],                      // the S6 card part schema — graded by js/grader/index.js, same code as originals
  hints: [3], solution: [{say, math}], misconceptions: [{part, answer, tag, msg}],
  skills, needs, tier, par, module, sheet, forCards,
}
```

**Rendering a generated figure** (there is no `data/figures.js` entry — the spec travels with the item):

```js
import { render, element } from '../figure/svg.js';
import { resolve } from '../figure/model.js';
const svg   = render(item.figure.spec, item.figure);        // string (memoised on the generated id)
const node  = element(item.figure.spec, item.figure);       // browser
const model = resolve(item.figure.spec, item.figure);       // = templates.modelOf(item)
```

**Grading a generated figure item**: pass the resolved model on the ctx —
`grade(part, raw, { model, figure: model, card: item, misconceptions: item.misconceptions, state })`.
`T-fig-pairs` also carries the spec on the part, so it grades even with a bare ctx.

## Decisions worth knowing

* **Generated figures never enter `data/figures.js`.** Each item carries a complete, self-contained `spec`
  with a unique `G-…` id (so `svg.render`'s memo key never collides). `data/figures.js` stays exactly the five
  hand-modeled scans.
* **The drawing never encodes the answer.** Bisect variants always draw an off-centre split; xlines/system
  variants draw a plausible angle unrelated to the algebra. Every one of them carries the "Not to scale" chip
  automatically (the labels contain letters), which is also what the printed sheets mean.
* **`T-fig-pairs` measures are drawn to scale** (no expression labels), so the feedback line
  "64 + 26 = 90 — complementary" is true of the picture the student is looking at.
* **A rejected root is never a "stray half"** — it has to push a labelled measure to ≤ 0 or ≥ 180, which is
  what the reason menu can actually say.
* **`T-fig-system` never draws a near-square crossing** (the drawn upper-left angle is pushed out of
  76°–104°), so nothing reads as an unmarked right angle.
* **Wedge ids** on `multi` fields and `cases` columns are `angleId(x, y)` (`'C-D'`), or the `UL/UR/LR/LL`
  aliases on `T-fig-system` — the same strings `wedgeEl()` resolves.
* Every misconception tag emitted here already exists in `data/misconceptions.js` (checked by the harness):
  `vertical-set-180`, `linear-pair-set-equal`, `assumed-bisects`, `midpoint-not-equal`, `forgot-second-root`,
  `rejected-valid-root`, `kept-invalid-root`, `missing-case`, `swapped-fields`, `sign-flip`, `arithmetic`,
  `half-side-perimeter`, `forbidden-reason`, `confused-vertical-linear`, `confused-comp-supp`, `not-adjacent`,
  `adjacent-as-nonexample`.

  ~2.4 ms/item; if Infinite mode ever feels slow, `lint` could return its layout.
