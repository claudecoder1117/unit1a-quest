## 1. What was built

### The two ladders, on one button row

`call.js` is the public authority for the rating pipeline. It owns four things:

1. **The CARRY ladder** — `EV = q·W − (1−q)·P`, strictly increasing in `q`. `evTable`, `evFor`,
   `argmaxCall`, `carryIndifference`, `evMaxBands`.
2. **The RATING ladder** — the Brier credit `c(p, o) = 10 − 40(p − o)²`, strictly proper.
   `credit`, `expectedCredit`, `dExpectedCredit`, `honestCall`, `ratingIndifference`.
3. **The window** — `w = 4q̂(1−q̂)`, the `w ≥ 0.25` informative gate, and
   `rating = clamp(0, 10, 5 + 2·Σ(w·c)/N)` with **N = 50 fixed**. `weightFor`, `isInformative`,
   `informativeBand`, `callEntry`, `windowPush`, `ratingFrom`, `ratingDetail`, `expectedRating`.
4. **Rank and `q̂`** — `rankFor`, `rankOf`, `rankNameFor`, `meanWcFor`, `callsFor`, `canCall`,
   `qHatFor`, `qHatDetail`.

Not one numeral of either ladder is written in `call.js`. The suite proves it the hard way: **there
is not a single decimal literal in the file**, and the only integer literals are `0-4`, `6`, `9`,
`10`, `12`, `100` — array indices, the quadratic-formula coefficient, the digits of `1e-9` /
`10 ** dp` / `1e-12`, `round(w, 6)`, and the ×100 that turns a width into percentage points.

### Global law 6, enforced in code and in the lint

`argmaxCall`, `honestCall`, `evTable`, `evMaxBands` and `regretOf` carry a banner comment saying they
are **Settings-and-debrief only**, and two tests enforce it:

- every `COPY` template in `data/job.js` is rendered with a stub proxy and greped for
  `argmaxCall` / `evTable` / `EV-max` / `evmax`. A deep walk over **every string value of every
  export** of `data/job.js` finds exactly one hit: `COPY.regret2`, the debrief line. The scanner is
  proved to have teeth against a planted needle.
- every file under `site/js` that references `argmaxCall` / `evTable` / `evMaxBands` must be in
  `{js/job/call.js, js/screens/settings.js, js/screens/stats.js, js/screens/run.js}`. **`js/screens/job.js`
  is deliberately NOT on that list** — the job screen can never import the argmax. This is a forward
  guard: it passes today because only `call.js` references them, and it will fail the moment J6 wires
  one into a pre-call surface.

### `qHatFor` needs a card index — READ THIS, J5 / J6 / J7

`q̂` is the **first-try rate on that make over the trailing 10 attempts**, read from
`save.cards[*].history` (G2: *"Rung distributions are read from `save.cards[*].history`"*). A history
entry is one sitting, `{at, ok, attempt, hints, ms}` or its packed 5-array form; a first try is
`ok ∧ attempt ≤ 1` — **hints do not disqualify it**, because rung 1 (Gold-with-H1) is still a
first-try clear on G1's ladder.

The save does not record which skills a card teaches, and **`call.js` deliberately does not import
`data/cards.js`** — that is 236 KB, and Home paints the board on the cold-open budget (G7 "two
passes"; `tests/home-r2.test.mjs:147` already forbids a static `page.js` import for exactly this
reason, and J13 owns the ≤ 20 s criterion). So the caller passes the index it already holds:

```js
import { byId } from '../../data/cards.js';
qHatFor(save, 'FAC2', { cards: byId });          // → 0.7
qHatDetail(save, 'FAC2', { cards: byId });       // → { qHat: 0.7, hits: 7, of: 10, … }
```

`opts.cards` accepts `byId`, an id→skills map, a `Map`, an array of cards, or a function
`(cardId) => skills[]`. With no index it falls back to a save-resident `rec.skills` if one is there,
and otherwise returns `qHat: null` with **`source: 'no-index'`** — so a forgotten `opts.cards` is
diagnosable rather than silently indistinguishable from an empty history. A genuinely empty history
returns `source: 'none'`. **There is no fabricated rate anywhere**: `null` is the same honest answer
the guard gives on job 1 (`no data — uniform 1/3`).

Evidence flows to **every** skill on the card by default, which is exactly what
`mastery.applyOutcome(skills, item.skills, s)` already does. `opts.primaryOnly` restricts it to
`skills[0]`, the make the composer labels the item with.

## 5. Deviations and objections (the spec was implemented; these are recorded, not fixed)

### 5.1 `PUBLISHED.sanityRating.overcall`: the −4.90 numeral and its "95" label disagree

G3.1's sanity table labels its last row *"systematic over-calling (95 on `q̂ = .5` material)"* and
prints a mean `w·c` of **−4.90**. The formula gives:

- **95** on `q̂ = .5`: `E[c] = 10 − 40[.5(.05)² + .5(.95)²] = −8.10`, `w = 1.00`, `w·E[c] = ` **−8.10**
- **85** on `q̂ = .5`: `E[c] = 10 − 40[.5(.15)² + .5(.85)²] = −4.90`, `w·E[c] = ` **−4.90**

So **−4.90 is the 85 call, not the 95 call**. Both clamp the rating to **0.00**, so the table's
rating column (`overcall: 0.00`) is right either way and nothing downstream moves. J1 flagged this to
J2 (notes/J1.md §7) and J2 owns the table. Both numerals are asserted from the formula and
`expectedRating(0.5, {call: 95}) === expectedRating(0.5, {call: 85}) === 0` is asserted.

**Request to whoever next edits COMPOSED-GAME.md:** either change that row's mean to **−8.10** (keeping
the "95" label) or change its label to **85** (keeping −4.90). Do not change both.

### 5.2 `CALL_DISAGREEMENT_BANDS[0]` has `money` and `rank` swapped

`data/job.js` (transcribing G3.1) declares:

```js
{ from: 0.775, to: 7/9,   money: 85, rank: 70 }   // band 1  ← BACKWARDS
{ from: 15/17, to: 0.900, money: 95, rank: 85 }   // band 2  ← correct
```

The ladders say the opposite in band 1. At `q = 0.776`:

| | 70 | 85 |
|---|---|---|
| carry EV `q·W − (1−q)·P` | **0.9520** | 0.9488 |
| Brier `E[c]` | 2.816 | **2.828** |

so in `q ∈ (0.775, 7/9]` **money prefers 70 and rank prefers 85** — the bolder call is the one the
RANK wants, not the one the money wants. Band 2 behaves the way G3.1's prose describes (money 95,
rank 85). The prose generalisation *"money prefers the bolder call and rank prefers the honest one"*
is therefore true of band 2 only; band 1 is the mirror case, and it exists because the carry ladder's
cut (7/9 ≈ 0.7778) sits **above** the Brier's (0.775) at that rung and **below** it at the next one
(15/17 ≈ 0.8824 vs 0.900).

`disagreementBands()` **computes** `money` and `rank` rather than reading the labels, so nothing
downstream inherits the error. The suite asserts the computed truth `[[70, 85], [95, 85]]` AND
records the data file's labels, so if the data file is ever corrected the recording assertion fails
loudly and this note gets revisited.

**Request to J1's owner / whoever next edits `site/data/job.js` and COMPOSED-GAME.md G3.1:** swap
`money` and `rank` in `CALL_DISAGREEMENT_BANDS[0]`, and soften G3.1's one-line generalisation.
I did not edit the file: BUILD-POLICY §2, and J1 declares every constant there frozen policy.

Measured band widths: **0.278 pp** and **1.765 pp**, total **2.04 pp**. G3.1 says *"2.1 percentage
points wide on purpose"*; 2.04 is what the ladders give. Recorded, not corrected.

### 5.3 Both bands are half-open `(from, to]`, because both ladders break ties DOWN

At `q = 0.775` both ladders say 70 (the Brier ties and takes the lower rung), so the band does **not**
include its floor. At `q = 7/9` the carry ladder ties and takes 70 while the Brier has already moved
to 85, so the band **does** include its ceiling. Same one rung up: they agree at `15/17`, disagree at
`0.900`. Asserted explicitly, and the "outside the bands they agree" test uses `(from, to]`.
This follows from J1 §5.4's tie rule, which J2 adopts for both ladders as requested.

### 5.4 `rankFor` returns a NUMBER, not the `RANKS` row

`save.player.rank` is `2` in G7's schema, so `rankFor(rating) → 1..5` and `rankOf(rank) → RankRow`
are separate. `rankNameFor(rating)` gives `'Called 3'` directly. A 1e-9 epsilon is applied at the
thresholds so a rating computed as 6.5 is never Called 2 through float noise; the printed band tops
(4.9 / 6.4 / 7.6 / 8.8) are display rounding of "< the next threshold" and are not used as gates.

### 5.5 `callEntry` rounds the stored `w` to 6 dp — this is required, not cosmetic

`4q̂(1−q̂)` at `q̂ = 0.7` is `0.8400000000000001` in float64. Stored raw, a call entry is 76 bytes;
G7's budget is **63 B × 50 = 3.2 KB**. Rounded to 6 dp the entry is
`{"p":0.85,"ok":true,"w":0.51,"skill":"FAC2","at":1758000000000}` = **exactly 63 bytes**. The
rounding moves a rating by ≤ 1e-6 and is asserted not to move any published number.

### 5.6 `expectedRating` exists because a 50-call window cannot hold a fractional outcome

"50 truthful `q̂ = .85` calls yield 9.99 ± .02" is a statement about the **expectation**: a realised
window of 50 outcomes at `q = .85` has a rating standard deviation of ≈ **1.44**, so no single
simulated window can pin 9.998 to ±.02. The suite therefore asserts it twice — deterministically
through `expectedRating` (9.998000000000001) and empirically through `ratingFrom` itself over
**10 000** seeded windows (mean 10.0074). No `Math.random` anywhere: `rngFrom` from `js/rng.js`.

### 5.7 `regretOf` ships BOTH ladders, because `COPY.regret2` and G8 J6b disagree about which one

`COPY.regret2` prints `you called 85, EV-max was 95. cost 4 **rating**.` — a cost in rating units.
G8 J6b's acceptance says the regret lines equal *"`econ.regretLine` / `call.argmaxCall`"* — and
`argmaxCall` is the **carry** argmax, whose cost is in loot units. A rating cost quoted against a
carry argmax is incoherent unless the line is deliberately a money-vs-rank comparison.

`regretOf({call, qHat, ladder})` therefore takes `'rating'` (default — `best = honestCall`, cost in
credit) or `'carry'` (`best = argmaxCall`, cost in EV units). **J6b must pick one and write it down.**
My recommendation: use `ladder: 'rating'` and keep the words "cost N rating", because the debrief's
other number is the rating delta; if J6b wants the money argmax, the copy should read `cost N loot`.

### 5.8 A skill with no original cards has no `q̂` — by construction, not by bug

`CSARITH`, `FAC1` and `QUAD-CTX` (3 of the 19 makes) have **no cards in `data/cards.js`** today; they
are taught by generated Variants, and a Variant sitting writes `save.variants`, not
`save.cards[*].history` (`screens/card.js:922` vs the variant branch). So `qHatFor` honestly reports
`qHat: null` for them until an original exists. That is the correct reading of *"first-try rate on
that make"* from the source G2 names, but it has a consequence the layer must handle:

> **A call on a make with no `q̂` has `w = 0` and is NOT informative, so it never enters the rating
> window.** Combined with G3.1's own arithmetic this is already true of any make with fewer than 2
> attempts (`q̂` can only be 0 or 1, and `w(0) = w(1) = 0`), so a fresh student's first calls on any
> make score nothing. That is the spec working as written — the rating starts at exactly 5.00 and
> fills — but J6/J7 should print the honest `0/50 informative calls` line rather than implying the
> call was scored. `COPY.ratingLine` already says exactly that.

If the intended reading is that Variant attempts should feed `q̂` too, that is a **spec change**, not
an implementation choice: it needs a per-skill attempts log the save does not have today. Flagged,
not invented.
