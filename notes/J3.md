## 1. What was built

`site/js/job/guard.js` is the guard's **distribution** and the **Elo** dials. It deliberately does
not own the guard's *price*: `wingMult`, `wingPen` and `guardMultFor` stay in `job/econ.js` (J1) and
are re-exported from here, so the odds and the payout can never drift apart (notes/J1.md §7).

Five things live in it:

1. **The wings.** The four-way partition of the 19 skills, and the `tag → wing` resolution that runs
   through `data/misconceptions.js`'s own 11 `AREAS` plus the 11-entry `AREA_WING` map in
   `data/job.js`. No new taxonomy; not one of the 68 tag records is edited (G4, G12 #15).
2. **`v_i`, the wing's study value** — `Σ_targets L · scope · cold`, with `scope` from `xp.scopeFor`
   verbatim and `cold` from `econ.coldFor` (the capped, interval-scaled term of G2, so a rotting card
   inflates nothing).
3. **`x̂`, stake-weighted over the last 10 jobs** — `ω_j = min(posted_j, 0.25 · Σ_k posted_k)`
   (G12 #12) — and the published draw `y = project((1−ε)x̂ + ε·uniform_n, 0.75)`, with the
   water-filling projection, the rank-driven `ε`, G4's three-in-a-row cap, and the seeded draw.
4. **The mixed equilibrium** — `v_i(1 − y_i) = k`, `k = (n−1)/Σ(1/v_i)`, with support trimming — and
   the 3-token pre-press the primary button uses.
5. **Elo** — symmetric, `K = 24`, the seeds, the win/loss outcome, the flow-control penalty that
   moves `R_player` and nothing else, and the vault grade that reads `R_player` and nothing else.

Every constant comes from `data/job.js`: `WINGS`, `WING_IDS`, `WING_OF_SKILL`, `AREA_WING`, `GUARD`,
`ELO`, `VAULT_GRADE`, `RANKS[].eps`, `COPY.guardColdStart`. Not one number is restated in code.

## 2. Exported API — exact signatures

### Wings and tags

```js
export { WINGS, WING_IDS, GUARD, ELO, VAULT_GRADE }     // re-exported from data/job.js
export { guardMultFor, wingMult, wingPen }              // re-exported from job/econ.js (J1 owns them)
export const WING_WEIGHTS: Readonly<Record<string, number>>   // {RECALL:32, FIGURES:26, WORDS:23, ALGEBRA:19}
export const AREA_IDS: readonly string[]                      // the 11 AREAS ids, in their own order

wingOf(skillId: string): string | null              // one of the 4 wings, or null for an unknown make
wingOfArea(area: string): string | null             // AREA_WING; 'general' → null BY DESIGN
wingOfTag(tag: string, forSkill: string|null = null): string | null
areaOfTag(tag: string): string | null
```

`wingOfTag` resolves a tag through its area. The three `general`-area tags (`sign-flip`,
`arithmetic`, `swapped-fields`) have no wing of their own and resolve to **the target card's own
wing**, so pass the make as the second argument wherever one exists. An unknown tag returns `null`
rather than throwing — saves carry retired tags and `misconceptions.lookup()` degrades the same way.

### The wing's study value

```js
targetFrom(item: object): { skill, tier, bucket, overdueDays, scope?|scopeFlags, loot?, cold? }
wingValues(save: object|null, queue: object[]): {
  byWing: Record<string, number>,      // v_i per wing, 0 for a wing the board does not touch
  values: number[],                    // the same, in WING_IDS order
  wings: string[],                     // WING_IDS
  support: string[],                   // the wings with v_i > 0
  perTarget: { id, skill, wing, value }[],
  unassigned: number,                  // value carried by targets with no known make
}
```

`queue` is `composePage`/`draftUnion` output: it reads `skill`, `tier`, `isReview`/`isVariant`/
`role`, `bucket` and `overdue` off the item, falling back to `save.cards[id]` for a missing
bucket/overdue. It reads **no clock** — a review item already carries its own `overdue`.

### `x̂` and the heat window

```js
heatWindow(save): { jobs: {shares: Record<string,number>, posted: number}[], source: string }
xHatFrom(save): {
  byWing, values, wings, jobs, weights: number[], cap: number, totalPosted: number,
  coldStart: boolean, source: 'heat.window'|'game.log'|'heat.press'|'none',
}
pushHeat(heat: object|null, entry: {press|tokens|shares: object, posted: number}): object   // PURE
```

`xHatFrom` reads, in priority order: `save.game.heat.window` (the authority — see §7 Requests),
`save.game.log` entries that carry a press, then G7's scalar accumulator `heat.press`/`heat.weight`
as a documented last resort (uncapped; the 25 % cap cannot be recovered from a scalar).
`pushHeat` returns a NEW heat object and maintains both the window and the accumulator.

### The projection and the published distribution

```js
project(y: number[], cap = GUARD.cap): number[]
projectWithPasses(y: number[], cap = GUARD.cap): { y: number[], passes: number }

rankOf(save|number): 1|2|3|4|5                  // save.player.rank, clamped; 2 is the schema default
epsFor(save|number): number                     // RANKS[rank].eps — 0.25 at Called 1 → 0.10 at Called 5
blockedWing(save, support = WING_IDS): string|null      // G4 "Mercy": the three-in-a-row cap

guardDist(save, eps?: number | {eps?, cap?, support?, wings?, blocked?}, cap?: number): {
  wings: string[], n: number, eps: number, cap: number,
  xHat: number[], mixed: number[], y: number[], passes: number,
  byWing: Record<string, number>,
  blocked: string|null, coldStart: boolean, jobs: number, source: string,
  note: string|null,                            // COPY.guardColdStart({n}) on job 1, else null
}
guardBars(dist): { wing, p, pct, blocked }[]    // whole percentages that still sum to 100
```

The support (the wings the drafted contracts touch) is taken from `opts.support`/`opts.wings`, then
`save.support`, then `save.inProgress.game.support`, then the wings present in
`save.inProgress.game.tokens`, then all four wings.

### The draw

```js
drawGuard(dist, seed: string|number): string | null
drawGuardIndex(dist, seed: string|number): number        // −1 on an empty distribution
```

`dist` may be a `guardDist()` result, a `{wing: p}` map, or a bare probability array. Seeded through
`rngFrom('guard', String(seed))` and nothing else, so the job seed pinned in `inProgress.game`
replays the draw exactly (G3.7 proof 6 — no reroll exists).

### The equilibrium and the press

```js
fixedPointMix(values: number[] | Record<string, number>, wings = WING_IDS): {
  y: number[], wings: string[], k: number, support: string[],
  byWing: Record<string, number>, dropped: string[],
}
pressAdvice(dist, values): {
  wings, y, v, marginal: number[],               // 0.25 · v_i · (1 − y_i) — the EVIDENCE
  equilibrium: number[], k: number, support: string[],
  tokens: Record<string, number>,                // the 3-token pre-press, largest remainder
  total: number,
  byWing: Record<string, {y, v, marginal, tokens, equilibrium}>,
  bestResponseWing: string|null,                 // DEBRIEF / Settings ONLY — see the warning below
}
```

> **Global law 6.** `pressAdvice.tokens` is the **equilibrium mix**, which G1 explicitly sanctions as
> the primary button's pre-press ("Tokens pre-pressed at the equilibrium mix, `Enter` to accept").
> `bestResponseWing` is the greedy argmax and is the guard's analogue of `call.argmaxCall`: it
> belongs in the debrief and in Settings, **never on a pre-press surface**. J12's lint should treat
> it exactly as it treats `argmaxCall`.

### Elo

```js
expectedScore(rPlayer, rHouse): number                   // 1/(1 + 10^((rh − rp)/400))
elo(rp, rh, outcome: 1|0|0.5|boolean): {
  player, house, delta, deltaHouse, expected, expectedHouse, k
}
eloOutcome({ bagged, posted }): 1 | 0                    // 1 iff BAGGED ≥ posted
eloSeed({ placementScore, skipped }): { player, house, placement: boolean }
flowControl(save | log[]): { fire, deltaPlayer, deltaHouse: 0, foothold, jobs }
applyFlowControl(eloState, save|log[]): { player, house, flow }
vaultGradeFor(rPlayer: number): 2 | 3 | 4
vaultGradeRowFor(rPlayer: number): { tier, tierMax, from, to }   // `to` is EXCLUSIVE
```

## 5. Deviations and objections (the spec was implemented; these are recorded, not fixed)

### 5.1 "a 3-RUN + 1-VAULT farm moves `x̂` by < 0.08" is true for a realistic window and false for a JOB-10-only one

The claim is scenario-sensitive and the document does not name the scenario, so the suite measures
five and asserts all five numbers. `x̂` is scale-invariant, so only the *ratios* of the shapes' posted
values matter, and those come from `econ.lootMean(shape) × targets`:
`RUN 36 · JOB-10 84 · JOB-12 152 · VAULT 162` — which reproduces G3.4's own "a RUN contributes about
a fifth of a VAULT" (0.222).

| the student's real 10-job window | decoy shift, stake-weighted | unweighted | reduction |
|---|---|---|---|
| 7×JOB-10 + 2×JOB-12 + 1 VAULT (the week the plan serves) | **0.0710** ✓ | 0.2000 | 2.82× |
| 10× VAULT | **0.0580** ✓ | 0.2000 | 3.45× |
| 10× JOB-12 | **0.0614** ✓ | 0.2000 | 3.26× |
| 9×JOB-10 + 1 VAULT | **0.0821** ✗ | 0.2000 | 2.44× |
| 10× JOB-10 | **0.1034** ✗ | 0.2000 | 1.93× |

**The objection.** Three 6-target RUNs are **108 posted against a JOB-10's 84** — they are 18 real
answered targets, not throwaway work, so stake weighting *cannot* make them weightless and should not
be expected to. The mechanism's real guarantee is the one the suite asserts unconditionally: a job's
influence on `x̂` is proportional to its posted value, capped at 25 % of the window's posted total,
and changing the press on a subset of jobs moves `x̂` by at most that subset's weight share (property
test, 2 000 random windows). The published "< 0.08" holds whenever the window contains any plan-sized
or vault work and is out by 0.023 for a window of nothing but the default evening job.

**Request to whoever next edits COMPOSED-GAME.md:** either name the window in G3.4 ("< 0.08 in a
window containing plan-sized or vault work") or move the published number to **< 0.11**. Do not
change `GUARD.jobWeightCap` to chase it — the cap is not what binds here.

### 5.2 "no single job exceeds 25 % of the window" is 25 % of Σ **posted**, not 25 % of the weight

`ω_j = min(posted_j, 0.25 · Σ_k posted_k)` bounds `ω_j` against the window's *posted* total. It does
**not** bound `ω_j / Σω` at 25 %: with three RUNs (36 each) and one job posted 100 000, the cap is
25 009 and the survivor still holds **99.9 % of Σω**, because the cap itself grows with the job.
Both readings are asserted — the formula's version as the contract, the share-of-weight version as a
recorded counterexample. The formula is the authority (BUILD-POLICY).

### 5.3 The water-filling loop needs a persistent `capped` set to hit its own ≤ n−1 bound

G3.4's pseudo-code recomputes `over = {i : y_i > cap}` each pass and sets `free = {i : i ∉ over}`,
which returns a just-capped index to `free` on the next pass. Read literally that loop still
converges (the excess shrinks geometrically) but it can take **more than n−1 passes** and, on
`[0.49, 0.49, 0.02]` with `cap = 0.4`, oscillates for several rounds. The document's own "terminates
in ≤ n−1 passes" forces the monotone reading, so `projectWithPasses` keeps a `capped` set: a capped
index never returns to `free`. Every pass then retires at least one index, and at least one index
always stays free whenever `n·cap ≥ Σy`. The worked n = 3 and n = 2 cases are unaffected (1 pass
each). **Settings prints the pseudo-code; the printed block should gain the words "an index that has
been capped stays capped" or J7's panel will not match the code.**

### 5.4 The vault-grade bands are half-open on their lower bound

`VAULT_GRADE` publishes `{from: 1000, to: 1199}` and `{from: 1200}`. Elo ratings are fractional after
the first update (`K·(o − E)` is never an integer), so a closed `≤ 1199` reading drops
`R_player = 1199.4` through the floor to tier 2. `vaultGradeRowFor` therefore treats the bands as
half-open — `[1000, 1200)` and `[1200, ∞)` — and its returned `to` is the **exclusive** upper bound.
The three published boundary values (999.9 → 2, 1000 → 3, 1200 → 4) are unaffected and asserted.

### 5.5 `x̂` needs a per-job window; G7's `heat` schema only publishes a scalar accumulator

G7 declares `game.heat = { press: {WING: n}, weight, jobs }`. The 25 % cap is
`min(posted_j, 0.25 · Σ_k posted_k)` over the window, and `Σ_k posted_k` changes as jobs enter and
leave — **it cannot be recovered from a running sum.** So `guard.js` reads (and `pushHeat` maintains)
`game.heat.window`: the last 10 `{press: {wing: tokens}, posted}` records. The scalar accumulator is
still written and is still used as an uncapped last resort, so nothing breaks if a caller never fills
the window. Cost: **10 × ≈ 60 B ≈ 0.6 KB** on top of G7's budget line for `crew/heat/backchecks/
ledger/commit`; the stated total still has 8 KB of margin. Request to J10 in §7.

### 5.6 `guardDist`'s support defaults to all four wings, not three

G1's walkthrough prints `no data — uniform 1/3` because that board spans three wings. With no support
supplied, `guardDist` uses all four and the note reads `1/4`. That is the honest default for a caller
that has not drafted yet; J5/J6 must pass the drafted support (the suite pins the n = 3 wording).

### 5.7 `bestResponseWing` exists and is debrief-only

§3.4 defines the best response ("dump tokens on `argmax v_i(1−y_i)`") and the 500-job convergence
acceptance needs it, so it is computed and exported. Global law 6 makes it debrief/Settings material,
exactly like `call.argmaxCall`. The pre-press value the board should use is `pressAdvice().tokens`,
which is derived from the **equilibrium mix**, which G1 explicitly sanctions.
