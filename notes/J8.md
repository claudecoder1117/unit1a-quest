## 1. What the ticket is really asking, and the one thing that makes it hard

G1 publishes the split as `game s / (answer s + game s)` where `game s = fixed phases + per-target
decision seconds`, and the fixed phases **include `debrief: 65`** (of the JOB column's 160 s) — the
time the student spends reading the debrief.

`js/job/state.js` sets `phase = 'debrief'` inside `endJob`, and one line later the record is gone
(`finishPage(save)` nulls `inProgress`, or `delete save.inProgress.game` on an early exit). So the
65 s G1 counts is **the one phase a job cannot measure about itself**: when the debrief's numbers are
frozen, that duration is still in the student's future.

That is not a nitpick, it is the whole shape of the ticket. Measured at `endJob`, a canonical JOB-10
default walkthrough banks `tGame 255 s / tAnswer 420 s` → **37.8 %**, and G1's cell is **43.2 %** —
5.4 points out, i.e. the acceptance number is unreachable on the accumulators alone. Every honest
route was measured before one was picked:

| route | JOB-10 default | what it costs |
|---|---|---|
| print `tGame/(tGame+tAnswer)` and call it the split | 37.8 % | the acceptance number fails by 0.4; the board printed 43 % twelve minutes earlier and the student sees two different numbers for one session |
| bank the debrief phase when the student leaves it | 43.2 % | correct, but it can only be *written*, never *printed on the debrief itself*; needs `endJob`/screen lifecycle work outside this ticket |
| move the debrief out of `game s` in the published table | n/a | contradicts G1 statement 3 and every printed surface (board, primary button, `plan.endsFor`) |
| **print the measurement as the headline and the credited session beside it** | **43.2 %** as the second number | one estimator, from `save.game.ledger.phaseMeans.debrief`, on a save key the board's own projection already reads — and it never stands alone |

The fourth is what shipped, in that order: **the headline is the measurement** (`38 % game`) and the
credited session prints beside it (`43 % with this screen`). The order matters and was changed after
the browser run: a credited headline reads *82 %* on a 26-second walk, because a fixed 65 s credit
dominates a short session. Measured-first has neither problem, and it is the number the board's own
ledger projection prints from job 2 onwards — the one screen where they can disagree is job 1, where
the board says `projected` in as many words.

## 2. The exported API

### `site/js/screens/run.js`

```js
/**
 * J8 — the split line in the debrief.
 * @param {object} job     a `state.debriefOf` object (tGame, tAnswer, wall)
 * @param {object} [save]  for `save.game.ledger.phaseMeans.debrief`
 * @returns {{split:number, measured:number, credit:number, game:number, wall:number, idle:number}}
 */
export function sessionSplit(job, save = null)
```

* `split` — **the session**: `(tGame + credit) / (tGame + credit + tAnswer)`. G1's basis. What the
  board's job-1 fallback, `plan.endsFor` and the published table all spend.
* `measured` — **the job**: `tGame / (tGame + tAnswer)`, identical to `debriefOf(save).split`. What
  `save.game.log[]` stores and what the board's *ledger* projection reads back.
* `credit` — `phaseMeans.debrief × 1000` (the shipped 65 s until the student has their own).
* `idle` — `job.wall − (tGame + tAnswer)`: the time that fell outside every phase. **0**.
* Pure. No DOM, no clock, no write — safe to call from either debrief surface or from a test.

The line it renders (`run.js`, the Page Summary debrief — G7's "the Page Summary becomes the
debrief"):

```
Split   38 %    4:15 deciding / 7:00 thinking · 43 % with this screen · 0 ms idle
```

and in `screens/job.js`'s in-screen debrief:

```
38 % game · 43 % with this screen · 24 decisions · 2.4 per item · 0 ms idle · posted 100
```

## 5. Open issues

### 5.1 The VAULT's second brief window has nowhere to land (J1 open issue 2, now measured)
`BOARD.briefAfterTargets = [4, 8]` and a VAULT is 7 targets, so the second window never opens.
Measured cost: the VAULT's fixed column over-counts by **20 s default / 50 s full**, which is
**1.3 / 4.3** points of split and **one** decision (17 measured against G1's 18). Both are inside the
±5 band, so nothing fails — but the published VAULT row is unreachable as written. Two clean fixes,
either of which I will re-measure on request: `briefAfterTargets` becomes shape-aware (`[3, 5]` for a
7-target shape), **or** `FIXED_PHASES.JOB` gains a VAULT column at 140/232. **Owner: J1 (`data/job.js`)
with J6/J5c.** `tests/job-split.test.mjs` §5.1 asserts the *measured* count against
`published.mandatory − (declared briefs − landed briefs)`, so it stays green under either fix and
tightens automatically when one lands.

### 5.2 `crew` (25 s) is in `GAME_PHASES` but not in `phaseMeans`
`PHASE_MEANS_DEFAULT` has five keys (`board · guard · brief · getaway · debrief`); the full-use
column also spends **crew: 25**. So the full-use session is credited 65 s and spends 90 s, which is
the 1.2–1.5 points of Δ on every full-use row. Adding `crew: 0` to `PHASE_MEANS_DEFAULT` would close
it (≈ 20 B in the save). **Owner: J1 / J10.**

### 5.3 `ledger.phaseMeans` can never move off its defaults today
`endJob` folds `g.ph[phase]` into `phaseMeans` for the five mean-phases, but `ph.debrief` is always
**0**: `setPhase(g, 'debrief', now)` is the last thing `endJob` does, and the record is deleted before
that phase ever ends. So `phaseMeans.debrief` is permanently the shipped 65 s, and the credit in
§2 is permanently the brochure's number rather than the student's own. It is the right number
(65 s is G1's), and it is labelled — but it is an estimator that cannot yet learn. The fix is in §6
(Request 2) and is the same lifecycle work that would let the app *measure* the debrief read.

### 5.4 The board's projection is shape-blind
The shipped ledger branch averages the last 5 jobs' `tGame`/`tAnswer` **whatever shape they were**,
so a student whose last five were RUNs is projected at ~45 % for a JOB12 that will measure ~34 %.
The corpus here never mixes shapes (it does not have to, to make the agreement criterion true), so
this does not fail anything — but it is a real 10-point error waiting on a real week. §6's projection
is per-shape and per-draft and does not have it.

### 5.5 `RUN.full.phases` is filled in here, not in `data/job.js` (J1 open issue 1)
G1 publishes RUN's full-use fixed **total** (130 s) without its per-phase split. The walkthrough
spends this allocation, which sums to exactly 130 and grows only the two optional surfaces a RUN has:

```js
RUN: { full: { phases: { board: 26, guard: 12, brief: 32, getaway: 20, debrief: 40, crew: 0 }, total: 130 } }
```

(+14 board, +12 brief, in the JOB column's own 37:30 growth ratio.) Only the **total** is G1's; the
allocation is this ticket's measurement and is asserted to sum to it. **`data/job.js` is J1's file —
the constant is theirs to add; `phasesFor()` drops its fallback the day it lands.**

### 5.6 `debriefOf` counts a brief window as one decision
G1's full-use column counts the *options taken inside* a window (up to 5); `state.js`'s `debriefOf`
counts `briefs.length`. Counted G1's way the measured full-use JOB is **33 + 2 Backchecks = 35**,
exactly G1's number — so the arithmetic is right, but the number `debriefOf` returns (25 on a clean
full-use run) is the mandatory-style count, not the full-use one. The debrief prints both the
measured count and the published `24 mandatory / 35 full use`, so nothing on screen is wrong.
`brief()` records `took[]` already; `debriefOf` could sum it in one line. **Owner: J5c.**

### 5.7 A Backcheck spend costs no phase seconds — but a miss lengthens the job
Asserted in §5.3 of the test file: the two spends add exactly 2 decisions and **0 ms**; the whole
`tGame` difference between a clean and a spent full-use run is the **two Rematch targets** the two
misses queue (`2 × DECISION_SECONDS[1]`). That is the study layer behaving correctly (no item is ever
removed from the schedule), and it is why the split walkthroughs run clean — G1's own note says a
Backcheck spend is "a decision but not a phase".

### 5.8 The board read and the guard reveal are not measured by the shipped screen — **the biggest gap**
`screens/job.js startOrGo()` calls `state.startJob(s, { now: now() })` and `state.beginTargets(s,
{ now: now() })` **in the same tick**, so:

* the `board` phase — G1's **18 s** default / **55 s** full-use read-and-draft — is banked as ~0: the
  record does not exist while the student is reading the board;
* the `guard` phase — G1's **12 s** — never opens at all (the machine goes `board → envelope`).

Measured in chromium (`qa/job-clock.mjs`): **parked 3 002 ms on the board → 2 ms banked**. Together
with the debrief (§1) that is **95 s of the JOB default column's 160 s of fixed phases** that G1
counts and the record cannot see, which is why a real session measures ~35 % where the scripted
walkthrough (which ticks those phases explicitly, as G1 publishes them) measures 37.8 %.

The fix is one argument and it belongs to J6 — Request 5 below. Until it lands, `qa/job-clock.mjs`
prints it as a **warning**, not a failure, because no acceptance line of this ticket depends on it.

that will actually land:

```js
function projectFor(save, drafted, budget) {
  const means = { ...PHASE_MEANS_DEFAULT, ...(save?.game?.ledger?.phaseMeans ?? null) };
  const queue = drafted.queue ?? [];
  const shape = SHAPES[budget.id];
  const landed = Math.min(shape.briefs, BOARD.briefAfterTargets.filter(n => n < queue.length).length);
  let answerS = 0, decisionS = 0;
  for (const it of queue) {
    answerS += ANSWER_MINUTES_PER_TIER[it.tier] * 60;
    decisionS += DECISION_SECONDS[it.tier];
  }
  if (!queue.length) { answerS = (drafted.minutes ?? budget.minutes) * 60; decisionS = budget.decisionS; }
  const gameS = means.board + means.guard + means.brief * landed + means.getaway + means.debrief + decisionS;
  const log = (save?.game?.log ?? []).filter(e => Number.isFinite(e?.tGame)).slice(-5);
  const jobs = Math.min(5, Math.max(log.length, Math.max(0, save?.game?.ledger?.jobs ?? 0)));
  return {
    split: round((100 * gameS) / (answerS + gameS), 0),
    jobs, source: jobs > 0 ? 'ledger' : 'projected',
    wallS: answerS + gameS,
  };
}
```

signal a returning student leaves — `log[]` (what the shipped code reads) or `ledger.jobs` (which
`endJob` already increments) — so **`job-board.test.mjs:971-979` keeps passing exactly as written**:
it sets `game.log` and gets `'ledger'` and `your last 2 jobs`. Its line 980 (`b.split === round(100 ×

## 8. What a later ticket should know

* `walkthrough()` in `tests/job-split.test.mjs` is the only harness in the suite that drives the
