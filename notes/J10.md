## 1. What was built

### The schema, v2

Two top-level keys, exactly as G7 specifies, and for exactly G7's stated reason: `store.js:192`
archives **top-level keys only** (`for (const k of ARCHIVED_KEYS) entry[k] = save[k]`), so a split
expressed as `game.rating` / `game.crew` sub-paths would have been silently ignored by `archiveUnit`.
`job-save.test.mjs` asserts no entry in either key list contains a `.`, so that can never be
reintroduced by accident.

```
save.player   → KEPT_KEYS      rating{calls[],value,n} · rank · elo{player,house} · records{7}
save.game     → ARCHIVED_KEYS  crew · heat{press{4 wings},weight,jobs} · tags{≤68} ·
                               backchecks{held,mintedDay} · ledger{jobs,tGame,tAnswer,phaseMeans{5}} ·
                               log[≤30] · commit{kind,byMin,honored,bound}
CAPS.game     = { calls: 50, log: 30, tags: 68, bundles: 5 }
```

`inProgress.game` needs no schema work: `inProgress` is already preserved verbatim through
`migrate` / `pack` / `unpack`, and the suite proves the whole job record survives byte-identical.

### The migration, and why the repair lives where it lives

`MIGRATIONS[1]` does one thing — add the two keys — and works on a bare `{v:1}` with no other key
present (`state.test.mjs`'s chain test calls it that way). All *repair* happens in `fillDefaults`,
which runs on **every** migrate, so it covers the three cases that matter and the one-shot migration
covers none of them: a v2 save reloaded, an imported save, and a hand-edited save.

Both normalisers use `{...defaults, ...raw}` at every level, so **a key a later ticket adds inside
`player` or `game` survives a reload** — they are not whitelists. That is asserted.

### `tags[].days` (G12 #18)

`days` is a **number**, `lastDay` a string-or-null. A `days` **array** — the shape G7 rejected, worth
≈ 18 KB on its own — is collapsed to its length, and its last entry is promoted to `lastDay` when
none is recorded, so an old-shape save is repaired rather than dropped. Asserted on the default
record, on repair, on an explicit-`lastDay` conflict, and over all 68 records of a saturated save
after a full pack/JSON/unpack/migrate round trip.

### Offline

`site/sw.js`'s precache list was regenerated (`node qa/gen-precache.mjs`) and was **stale by three
files** other lanes had landed while this ticket ran: `js/job/call.js` (J2), `js/job/guard.js` (J3),
`js/gen/asn-reason.js` (J5b). It now carries 121 paths. Two tests guard it going forward:

* **the job-layer list** — every file under `site/js/job/`, plus `data/job.js`, plus
  `js/screens/job.js` and `css/job.css` once they exist, must be precached;
* **the offline closure** — a walk of every static `from '…'`, bare `import '…'` and dynamic
  `import('…')` outward from `js/app.js` (89 modules today). A specifier that resolves to a file not
  in `PRECACHE` fails, and so does one that resolves to nothing. This is the machine-checkable form
  of "airplane mode after one load runs a job start to finish": it is what actually caught
  `js/gen/asn-reason.js`. It also asserts the walk reached `js/store.js`, `js/screens/card.js`,
  `js/screens/run.js` and `js/page.js`, so it cannot pass vacuously.

## 2. Exported API — exact signatures

All new exports are from `site/js/store.js`. Nothing existing changed signature.

```js
export const SAVE_VERSION = 2;

/** CAPS gains one frozen sub-object; every S6 cap is unchanged. */
export const CAPS = Object.freeze({ … , game: Object.freeze({ calls: 50, log: 30, tags: 68, bundles: 5 }) });

export const KEPT_KEYS      // … + 'player'
export const ARCHIVED_KEYS  // … + 'game'

/** A brand-new `save.player` / `save.game` / one Fault Index record. Fresh mutable objects every
 *  call — never a reference into a frozen constant. */
export function freshPlayer(): object
export function freshGame(): object
export function freshTag(): { resolved: 0, triggered: 0, days: 0, lastDay: null, cleared: false, sealed: false }

/** raw → a well-formed key. Total (accepts anything), idempotent, cap-applying, unknown-key-preserving.
 *  Called by fillDefaults; exported for J2 / J7 and for tests. */
export function normalizePlayer(raw: unknown): object
export function normalizeGame(raw: unknown): object

export const MIGRATIONS = { 0: …, 1: (s) => ({ player, game, ...s, v: 2 }) };
```

`tests/_helpers.mjs` gains five pure fixtures (node builtins only, nothing imported from `site/`,
caps and clock passed in — the file's own house rules):

```js

export function worstCasePlayer(now, caps): object       // caps = CAPS.game
```

## 5. Deviations from COMPOSED-GAME.md / the ticket, and why

**1. `store.js` does NOT import `data/job.js`.** J1's note (§Requests → J10) asked for "the migration
should write `SAVE_DEFAULTS` rather than an inline literal". I implemented the *intent* — one source
of truth — without the import:

* `data/job.js` is **41 612 B** of constants. `store.js` is on the cold-open boot path of *every*
  screen (S9 #1: first answer ≤ 20 s, and `home-r2.test.mjs` already forbids Home a static import of
  `page.js`/`plan.js` for exactly this reason). A student with `settings.game = false` would pay for
  the whole game layer's constants on every boot.
* `SAVE_DEFAULTS` is **deep-frozen**. A migration that spread it would hand the app a frozen save
  that silently refuses every write — a whole bug class, now covered by a `doesNotThrow` test.
* Instead, `job-save.test.mjs` asserts `freshPlayer() ≡ SAVE_DEFAULTS.player`, `freshGame() ≡
  SAVE_DEFAULTS.game`, `freshTag() ≡ TAG_RECORD_DEFAULT`, `CAPS.game ≡ data/job.js CAPS`, and
  `BACKCHECK.max` clamps `backchecks.held`. Change either side and the other fails the same minute.

If the integrator prefers the import, it is a three-line change and the drift tests become
tautologies; say so and I will swap it.

**2. `state.test.mjs`'s size bound is now two bounds, not a raised one.** The pre-existing worst case
already measured **480 409 chars** against T01's `BUDGET = 500_000`; the schema's budgeted 25 KB
pushes it to 505 584. I did **not** raise 500 000. The test now measures the save *with the game
bytes removed* (`withoutGameKeys`) and asserts **that** against T01's unchanged 500 000 — the same
bytes T01 measured, still bound by the same number — and bounds the addition separately with G7's
own 25 KB. The total bound is therefore derived (`500 000 + 25 · 1024`), not invented.

**3. The shared fixtures live in `tests/_helpers.mjs`, not in `state.test.mjs`.** Importing an export
from a `.test.mjs` file drags its whole suite into the importer's process — `_helpers.mjs`'s own
header documents that trap (it is why `no-random.test.mjs`'s export is called out there). The
fixtures obey that file's house rules: pure, node builtins only, no `site/` import, and **caps and
clock are parameters**, so they cannot disagree with the shipped `CAPS.game`.

**4. Six lines of cap enforcement were added to `applyCaps`, which is outside "migration only".**
`applyCaps` runs on every `update()`; `migrate` runs only on load and import. Without this, a session
that plays forty jobs without ever reloading grows `player.rating.calls`, `game.log` and `game.tags`
past their caps and writes the overflow to disk on every debounce — a real, if slow, budget leak in
the one bound this ticket owns. The addition is O(1) unless something is over cap, is guarded for
junk like every other cap, and is idempotent. Flagged because it is a scope call, not a silent one.

**5. `crew` and `idx` are restored from where they actually live.** G1's prose lists "queue, idx,
loose, bagged, chain, calls, tokens, guard, crew, briefs" as `inProgress.game`'s contents, but G7's
key list (and J1's `IN_PROGRESS_KEYS`) contains neither `crew` nor `queue`/`idx`. The resolution I
implemented and tested: `crew` is restored because `save.game.crew` persists (and G2 says
re-allocation is free and unlimited, so it *should* outlive the job); `queue`/`idx` are restored
because they are the existing `inProgress` page record. Both are asserted. No new key was invented.

**6. One objection to the spec, recorded rather than fixed.** G7's per-line budget does not
reproduce at its stated figures even though the total does — see Open issues #1. Implemented as
written; the total is what the test binds.

## 6. Open issues

1. **The 25 KB bound has 425 B of headroom (24.58 of 25.00 KB), and G7's per-line figures are
   optimistic.** Measured against G7's table: `player` **3.59 KB** (G7: 3.5) · `game` **13.21 KB**
   (G7: 11.1) · `inProgress.game` **3.50 KB** (G7: 2.1) · runs delta **4.28 KB** (G7: 4.8). The two
   over-runs are honest worst cases, not padding: all 68 tag ids are given the length of the
   *longest* real tag (27 chars, against a real median of 15), and every one of the 5 bundles carries
   all 12 locks (the maximum replication `composeBundles` could produce). If **J5** puts more than
   `{id,label,overflow,wing,posted,minutes,grade,cold,locks[]}` on a bundle, or **J7** widens the tag
   record, this bound goes red. The per-line test is deliberately loose (2× each line) so only the
   total is binding; tighten it once J5 and J7 have shipped their real shapes.
2. **COMPOSED S6's "< 250 KB" does not close and did not close before this ticket.** The real
   saturated save is 480 409 chars *without* the game layer. `notes/T01.md` #1 measured this, listed
   the cap cuts that would be needed (history ≈ 6, runs ≈ 25, Scratch ≈ 200, Mock work ≈ 512) and
   asked the integrator to accept 500 000; nobody has ruled. **This is still an open decision for the
   integrator, not for J10.** G7's own arithmetic (210 KB stated + ≤ 25 KB added = 235 KB) is
   asserted and passes; the two statements are about different worst cases and both are now printed.
3. **The seed-pinning proof is the save layer's half only.** `guard.js` (J3) and `board.js` (J5) did
   not exist when this suite was written, so the three draws are modelled with `rng.js` directly. The
   property proved is exact and load-bearing — the pinned seed survives the disk verbatim and
   reproduces every draw made from it, across ten reloads — but it becomes *binding on the real
   draws* only once J3 and J5 derive theirs from `inProgress.game.seed`. See Requests.
4. **A corrupt `inProgress.game` is not repaired, only preserved.** `inProgress` is pass-through
   (`isObj(x) ? x : null`), exactly as it is for a half-finished Page today, so a job record damaged
   by a hand edit would reach `screens/job.js` malformed. Defending it belongs with whoever owns the
   resume path (J6 / the job state machine); say the word and I will add an `inProgress.game`
   normaliser here instead.
5. **`applyCaps` does not cap `inProgress.game.calls` or `.bundles`.** They are bounded by the job
   itself (≤ 12 targets, exactly 5 bundles) rather than by a cap, which is why `CAPS.game.bundles`
   exists as a *declared* number the board must honour rather than as an enforced trim. If J5 can
   ever post more than 5, it must enforce it — trimming a live job's bundles on a debounce would
   corrupt the job, so the save layer deliberately refuses to.

## 7. Requests for other file owners

**J2 (`js/job/call.js`) and whoever writes the rating push.** `save.player.rating.calls` is the
**window itself** — `CAPS.game.calls = 50`, newest kept. `applyCaps` trims it on every update, so a
push that does not trim is merely wasteful, not wrong; but `ratingFrom(calls, N = 50)` must keep
dividing by **N = 50**, not by `calls.length`, or a freshly-migrated save with 3 calls would score
off a 3-call window. The defaults ship `value: 5.0, n: 0, rank: 2`, which is G2's "calling 50 on
everything scores exactly 5.0 — Called 2 forever".

**J3 (`js/job/guard.js`).** The guard draw **must** be seeded from `inProgress.game.seed` (e.g.
`rngFrom('guard', save.inProgress.game.seed)`), never from `Date.now()`, a load counter or
`save.seedCounter`. G3.7 proof 6 is the anti-quit-scum device and it is the seed that carries it.
`job-save.test.mjs` proves the seed survives the disk; please add the assertion that `drawGuard`
reads it, so the two halves meet.

**J5 (`js/page.js`, `js/job/board.js`).** Same for the bundle partition and the ×2 placement — seed
both from `inProgress.game.seed` (G1: "seeded per `dateISO|jobIndex|targetIndex`" for the ×2). Also:
the worst case I measured gives each of the 5 bundles all 12 locks and the fields
`{id,label,overflow,wing,posted,minutes,grade,cold,locks[]}`. Anything wider than that eats the
425 B of headroom left under the 25 KB bound — tell me and I will re-measure.

**J6 (`js/screens/job.js`) and the job state machine.** Write `inProgress.game` with all sixteen
`IN_PROGRESS_KEYS` (J1's `data/job.js`) — the resume test asserts every one is present after a
reload. `crew` and `idx` are **not** among them: crew is read from `save.game.crew` and idx from the
existing `inProgress.idx`, and that is what the acceptance test checks. If you need a job-scoped crew
snapshot (G1's brief window re-ranks "for the rest of the job"), put it on `inProgress.game` — the
record is pass-through and will survive — and tell me so I can price it.

**J7 (`js/job/index.js`).** One tag record is
`{resolved, triggered, days: number, lastDay: string|null, cleared, sealed}` and `days` must stay a
**number**. `normalizeGame` will collapse an array to its length on the next load, so an array would
not corrupt anything — it would just silently lose the dates you thought you were storing. Sealing
(3 clean resolutions across 3 distinct days) has exactly a count and a last date to work with, by
design (G12 #18). The 68-tag cap is enforced on load and on every update.

**Every remaining J ticket.** You own nothing in `site/sw.js`, but **`sw.test.mjs` will fail your
run** the moment you add a file under `site/`. Run `node qa/gen-precache.mjs` before you finish — it
is a one-line, generated block. This ticket found the list stale by three files from three different
lanes in a single sitting.

**Integrator.** Two decisions are waiting on you, neither of them mine to take: (a) COMPOSED S6's
250 KB vs the real 480 KB saturated save (open since `notes/T01.md` #1); (b) whether `store.js`
should import `data/job.js` after all (Deviations #1). Neither blocks any later ticket.
