## 1. What was built

`#/run/job?seed=` — **no new route**. `run.js`'s `DELEGATES` table imports `./job.js` and calls
`mountJob(params, query)`, the same pattern `baseline` and `night` use. `ROUTE_PATTERNS` is still 13.

The screen is a thin renderer over `js/job/state.js`. Every number is `state.*`'s, every sentence is
`data/job.js COPY`'s, and each of G1's beats is one `render*()`:

```
board/guard  → the board sheet + the guard's published bars + the 3-token press + COMMIT + primary
envelope     → the SEALED envelope, the evidence line, the call row [50][70][85][95]
answer       → screens/card.js's answering body, mounted as-is (the board collapses to 36 px)
payout       → the payout line, the chain ticks, BAG / PUSH / Backcheck / CALL IT
brief        → re-press (guard redrawn) · re-rank crew · take or decline the tell · declare a minute
getaway      → the vault line, CRACK / WALK
debrief      → the outcome, the bag, the rating, the measured split, the decision count
```

### The three laws, made structural rather than promised

| law | the mechanism |
|---|---|
| **The seal** (G1, G3.7 proof 5) | `renderEnvelope` renders `state.envelopeFor()` and nothing else. It contains no `cardById[`, no `T.generate`, no `createCardView` and no `stemRefFor` — asserted by slicing that function out of the source. The stem is addressed **only** by `state.stemRefFor(save)`, which is `null` until `lockCall` (or `beginAnswer` on a no-stakes target), so there is nothing to render a stem *from* before the call. |
| **No pre-call recommendation** (Global law 6) | `screens/job.js` does not contain the strings `argmaxCall`, `evTable`, `evFor`, `evMaxBands` or `EV-max` anywhere. The call row is built from `envelopeFor().calls` alone, and the browser test compares the four call buttons **attribute for attribute** — a mark on the argmax rung would be a diff, not a judgement call. |
| **One grade path** (COMPOSED S1) | `createCardView` is called exactly once, from `renderAnswer`, after `stemRefFor` returns. `onDone` hands card.js's own result object to `state.applyTarget`. The file contains no `applyOutcome`, `scoreFor`, `rarityOf`, `xpFor`, `updateSkill`, `save.cards` or `save.skills`. |

### The board collapse, and why it is CSS and not JavaScript

```css
.job-screen:has(.card-screen) .job-board { block-size: 36px; max-block-size: 36px; overflow: hidden; }
.job-screen:has(.card-screen) .job-board-body { display: none; }
.job-screen:has(.card-screen) .job-board-line { display: block; … }
```

The collapse keys on **the stem's own presence**, not on a class the renderer has to remember to set,
so it cannot desync from the thing it is making room for. 36 px is `data/job.js LAYOUT.boardCollapsedPx`,
read through a custom property; the test asserts the number comes from that table.

### The header swap (G7, G10 #22)

`app.js` gains `setJobHeader({loose, bagged, chain})` / `setJobHeader(null)` and `headerItems()`.
During a job `hdr-level`, `hdr-streak`, `hdr-xp` and `hdr-combo` are hidden and `#hdr-loose`,
`#hdr-bag`, `#hdr-chain` are created next to the theme toggle: **five items during a job, six
outside one**, which is `HEADER.keptDuringJob (2) + addedDuringJob (3)` and
`keptDuringJob (2) + hiddenDuringJob (4)`. The three ids are literals in `app.js` on purpose — the
shell must not pull `data/job.js`'s 800 lines onto the cold-open path (S9 #1) — and the test asserts
the two lists are equal to `HEADER`'s instead of importing one into the other.

### Layout — the conventions, applied to the exact shape that caused the bug

This screen hosts a card inside a **new** container, which is the configuration that printed one
letter per line in the placement at 1900 px. So:

* `.job-board`, `.job-panel` and `.job-beat` each carry `container-type: inline-size; container-name: job`
  and are capped at `min(100%, var(--col))`. **Each is its own container** because each is narrower
  than the screen — querying one shared host would be the same bug one level down
  (notes/LAYOUT-ROOT.md §3 checklist #3).
* **`css/job.css` contains zero `@media (min-width: …)` rules.** Every column decision is
  `@container job (…)`. The test asserts the count is 0.
* Every `grid-template-columns` that holds words is `minmax(min(100%, N ch), …)` — a ch floor that
  can never exceed its own grid — and **the narrow form is the default**: the container query only
  ever *adds* columns, so a host below the threshold is one column, never a squeezed two.
* `.job-screen { max-width: none }` in every phase (job.css is linked after polish.css), with the
  reading panels carrying the `--col` cap themselves, so the screen's width does not change between
  the envelope and the stem — nothing moves under the student's thumb at call-lock.
* Nothing is `position: fixed`; the tile mint stays the product's only full-screen moment (G10 #13).
* Text colour is only ever an `-ink` token, so both themes clear 4.5:1 by construction
  (`theme.css`'s FILL-vs-INK rule), and the test fails on a `color: var(--ok)`-style fill.

### The six cues

`job-envelope-flip 180ms` · `job-call-lock-snap 120ms` · `job-loose-tween 300ms` ·
`job-chain-tick 150ms` · `job-guard-bars 250ms` · `job-bag-drop 600ms` — exactly
`data/job.js ANIMATION.cues`, by id and by duration, all `transform`/`opacity`, none of them a
rotate (G11 killed the envelope tilt: the "flip" is `scaleY` + `opacity`). `prefers-reduced-motion`
zeroes all six and changes no colour.

### The call sequence the screen actually runs (notes/J5c.md §2, verbatim)

```js
postBoard(save, today, { now })                     // the board, before a job exists
startJob(save, { picks, tokens, now, today, board, seed });  beginTargets(save, { now })
envelopeFor(save, { makeName })                     // SEALED — no id, no template, no stem
lockCall(save, 70, { now })    /* or */  beginAnswer(save, { now })   // stakes off → the other door

bag(save) | push(save) | endJob(save, finalWordOf(save))             // the continue tap, occupied
```

## 5. Deviations from COMPOSED-GAME, and objections (the spec was implemented; these are recorded)

### 5.1 `job` is in `KIND_META` but **not** in `RUN_KINDS` — one changed line in run.js
G7 asks for one `KIND_META` entry. `RUN_KINDS` is `Object.keys(KIND_META)`, and
`tests/run.test.mjs:50` asserts `RUN_KINDS` deep-equals **S1's eleven named run kinds**. Adding a
twelfth would have turned a test I do not own red, which BUILD-POLICY §3 forbids and which I may not
fix by editing that test. So the entry carries `game: true` and `RUN_KINDS` filters it:

```js
export const RUN_KINDS = Object.freeze(Object.keys(KIND_META).filter((k) => KIND_META[k].game !== true));
```

This is run.js's own existing reading: `post` is delegated on this route and deliberately never
listed in `RUN_KINDS`, with a comment saying why. The job is the game layer's mount point, not one of
S1's run kinds. **One line changed in a file I part-own; flagged here rather than done silently.**

### 5.2 Four `job-*` states added to `qa/audit-states.mjs`, a file I do not own
"run `node qa/layout-audit.mjs --only job` and make it clean" is an acceptance criterion, and
`--only` matches state-id prefixes from that catalog — with no `job-*` state the command measures
nothing and "clean" is unfalsifiable. The block is additive, marked `J6`, dev-only (nothing under
`site/` imports it, and it is never part of the deployed artifact). Request filed in §7.

### 5.3 The final target calls `endJob` directly instead of `push()`
`push()` on the last target ends the job through `state.advance()` → `endJob()`, but returns a status
rather than the debrief, and `endJob` → `finishPage` sets `save.inProgress = null` on the way out —
so by the time `push()` returns there is no record left for `debriefOf(save)` to read. The screen
therefore calls `endJob(save, finalWordOf(save))` on the last target and keeps the returned debrief.
`finalWordOf` duplicates three lines of `advance()`'s word choice, which is one duplication too many.
**Request to J5c in §7: have `push()` return the debrief when it ends the job.**

### 5.4 The header stays in job mode **through the debrief**
"Five items during a job" is measured at the debrief too (the walk reports 5 there). That is
deliberate and, I believe, required: G10 #13 puts the bag drop "in place in the header column" during
the debrief, which needs `#hdr-bag` to exist at that moment. The header returns to six the instant
the screen unmounts. If the integrator reads "during a job" as ending at the last answer, say so and
it is a one-line change in `syncHeader`.

### 5.5 `screens/card.js`'s dock Continue is **relabelled**, not duplicated
G10 #10: "the bag/push prompt IS the continue tap — it occupies that slot rather than replacing it."
card.js creates `#dock .card-continue`, focuses it after every grade, and binds Enter to it. So the
screen relabels that button to `PUSH ↵` (or `Finish` / `Next`) and puts `BAG` beside the payout line.
Reaching into another screen's DOM for a label is the ugliest thing in this file; the clean fix is a
`continueLabel` option on `createCardView`. Request in §7.

### 5.6 The brief window implements four of G1's five options (unchanged from J5c §5.8)
Re-press (with the guard redrawn from the pinned seed), re-rank crew, declare a minute, take or
decline the tell. **"Swap one undrafted contract in at its declined price" is not implemented** — it
rebuilds `inProgress.queue` mid-job, which is a schedule write, and J5c explicitly handed it to this
ticket. I did not do it either: a mid-job queue rebuild is a *composer* operation, and putting one in
the renderer is exactly the sort of second writer G9 #2 exists to prevent. Open issue #1.

### 5.7 The debrief is a placeholder for J6b
G7 gives the debrief to J6b as an extension of run.js's Page Summary, and `renderSummary` is
module-private in run.js. Until J6b lands, `renderDebrief` prints the honest minimum from
`state.debriefOf`: the outcome, `COPY.walk`'s line (bag · rating · rank · thinking/deciding ·
decisions), the split, the decision density, `COPY.ratingLine`, `COPY.leftOnPage` when targets remain
and `COPY.deflation`. **No tile mint, no skill bars, no Readiness delta** — those are J6b's, and
duplicating them here would be the second implementation G7 is trying to avoid. Request in §7.

### 5.8 The 22:00 close and a bound COMMIT are not polled by this screen
`state.quietClose` and `state.commitDue`/`commitFire` are pure and take the clock; G8 gives the
*trigger* and the copy to J11 (`tests/job-week.test.mjs`). The screen renders `COMMIT` and binds the
declaration; it does not watch the clock for it. J11's hook, noted in §7.

### 5.9 Two defects found by looking at the screenshots, not by a test — and the tests they grew
Recorded because "it passed the auditor" is not "it is right":
* **`null` printed twice** (once on the board, once on the envelope). `h()` drops null children;
  the native `Element.append()` stringifies `null` into the text `"null"`, and this screen is built
  out of conditional rows. Fixed with one `add()` helper, and `tests/job-screen.test.mjs` now asserts
  that the only direct `.append(` calls in the file are the three structural ones.
* **The `GUARD:` line named the wrong wing.** It was printed from the published distribution's first
  bar before the guard had drawn — i.e. it named a wing the House had not chosen, which is exactly
  the kind of fabricated pre-decision statement G11 rejects. It is now printed only once
  `guard.wing` exists, from the real draw, with the guarded wing marked and `mult: null` at zero
  tokens (`COPY.guardToken`'s own contract). Pinned by a test.

Neither was visible to any detector: the text was not collapsed, clipped, overlapping or low
contrast. It was just wrong.

## 6. Open issues

1. **The brief's contract swap** (§5.6) is still nobody's. It needs a `page.js` function that
   re-runs `draftUnion` with one more contract and re-writes `inProgress.queue` from the pointer
   onward. `state.brief(save, {...})` will record `'swap'` in `took` once someone pushes it there.
2. **`finalWordOf` duplicates `state.advance()`'s three-line word choice** (§5.3). It is asserted
   against `OUTCOMES` and covered by the walk, but it is a second copy of a rule and should die the
   day `push()` returns its debrief.
3. **`.job-say` clamps to one line while a stem is on screen.** The guard sentence is ~80 characters
   and 375×331 has no room for three lines of it; the collapsed board line already restates the
   guard. The region stays in the accessibility tree and keeps announcing (`display: none` would
   not), and the clamp declares `text-overflow: ellipsis`, so it is intent rather than an accident.
   If a sighted student should see the full line mid-answer, the honest fix is a tap-to-expand, and
   that is a design decision, not mine to take.
4. **The walk answers most targets by missing them to the worked solution.** `qa/job-screen.mjs`
   answers from the card's own data whenever the widget takes typed fields and otherwise produces a
   well-formed *wrong* answer until card.js's third-miss path fires — both are real paths through
   `screens/card.js`, and nothing is synthesised. The consequence is that the browser walk exercises
   the **miss** payout branch far more than the clear branch; the clear branch's copy is pinned in
   the node test against `COPY.clear` instead. A fixture whose first targets are all typed-field
   cards would close that gap.
5. **A one-target job has no getaway beat** (J5c §5.3) and ends `COMPLETED`; `finalWordOf` follows
   that reading. Nothing in the shapes table produces one, so it is untested in the browser.
6. **`requeueReview` can grow the job past `shape.targets`** (J5c open issue #2). The head's progress
   bar reads `queueOf(save).length`, so it stays truthful, but the board's `~N min` and the primary
   button's `N targets` are the *pre-draft* numbers and will read low on a bad review night.
