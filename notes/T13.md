## 3. Behaviour worth knowing

* **The clock is wall-clock and nothing else.** `remaining = startedAt + limitMs − Date.now()`, re-read every
  250 ms and on `visibilitychange`. Closing the tab for twelve minutes costs twelve minutes; reopening
  `#/mock` offers **Resume · 28:00 left · 7/20 answered**, restores the answers and puts the student back on
  the question they were on. A tab reopened past 0:00 gets an honest card ("ran out of time while the tab was
  closed — it will be graded as it stood") and one tap grades it with `auto:true`. Verified in Chromium.
* **Submit is idempotent**, guarded by `runs[n].status`: a second `submitRun` returns the same record,
  re-pays no XP, re-schedules nothing, logs no second error. Tested.
* **XP once per seed** (S4): `mockXp` refuses when any finished run with the same `seed` already paid, and a
  `retry:true` run pays nothing at all. PB (+200) is only against finished, non-retry runs of the same kind.
* **The `equation` slot is 40 %** of its item in the Mock. The screen mounts the setup as a *required* part
  (`ctx.mock`), and `grader/index.js combineCredit(entries, {mock:true})` does the split — answering only the
  setup on a section-D item scores exactly 2 of 5 points. Pinned by a test over every setup item on the paper.
* **No feedback until SUBMIT.** `setFeedback()` is never called, so no widget ever colours itself; the asn
  widget's letters stay live (the student can change a verdict); the rootcase stage rail is grey progress.
* **Progressive items** (`roots → keep/reject → cases`: ang-04/05/09/10, wp-12) get a **"Next step →"** button,
  and Enter inside one advances the STAGE, not the question. The roots the student typed are parsed silently
  (`grade()` for `res.found`, nothing displayed) and handed to the later stages so the keep/reject rows and the
  case tabs are built from *their* answer, not from the key.
* **Every miss** → the card's Leitner bucket via `schedule.applyOutcome(save, id, 'wrong')` with the test clamp,
  plus a `recordRematch` error entry (so T10's Rematch loop and the Patterns panel see it). **Mastery moves once
  per skill per paper**, judged on the state the run started in: a Mastered skill drops straight to 69 (S4), an
  unmastered one takes the normal EMA toward 0. Twenty items must not compound into twenty hits on one skill.
* **Blank ≠ wrong shape.** A widget's own `isEmpty()` decides whether an answer was given; several widgets
  answer `raw()` with a shape (`{kind:'ray', pts:[]}`) that is not blank by inspection. The question map, the
  "N unanswered" count and the report's "left blank" all read that one decision.
* **Autosave**: every widget change writes through `store.update()` (250 ms debounce); a 5 s timer and every
  `visibilitychange` → hidden call `flush()` and bump `tabAway`; leaving the screen mid-Mock captures and
  flushes too. Nothing is written when nothing moved.
* **After 21:30** a full Mock's rules card says "40 minutes runs past 22:00 — start anyway?" and the button
  becomes "Start anyway" (S7). The Baseline (20 min) does not ask.
* **The Baseline** is the same screen at 10 items / 20 min across all five sections, `kind:'baseline'`, scored
  ×0.8 into Readiness's `A` (`readiness.js MINI_KINDS`). `#/run/baseline` reaches it through T16's delegate,
  which looks for `mountBaseline` first — that export exists for exactly that reason.
* **The report's band word is scoped** ("Ready **on this paper**") because the Readiness line two rows below
  uses the same four words for a different number.
* **"RUN THE MISSES"** runs inline on the report rather than navigating: T09's `createCardView` is embedded for
  the missed items at their own seeds plus up to three siblings of the same templates (new numbers), with
  hints, XP and mastery written the normal way. See Requests → T16 if that should become `#/run/…`.

## 5. Open issues

1. **`daily[today].missesDrilled` is set when "Drill what I missed" is tapped**, not when the drill finishes —
   notes/T10.md §7 words the contract that way, and the report cannot see the end of a run it navigated to. If
   T16 sets it at the end of a `drill` run launched from a Mock report, delete the write in `report.js
   startDrill()` (three lines).
2. **A resumed progressive item restores its roots text and its stage, not the keep/reject rows or the case
   cells.** `widgets/rootcase.js` has no `ctx.values` restore (every other widget does), so the reject/cases
   stages come back empty on screen — but the answers the student already gave are still stored and still
   scored, because the Mock captures each stage's raw as it is left. See Requests → T08a.
3. **`work` (the scratch) survives only on the three most recent Mock-like runs** (`store.js CAPS.workRuns`).
   An older report prints "Nothing written here." rather than a stale blank. Correct per S6, worth knowing.
4. **`#/mock/report/:n` takes the runs INDEX**, not the Mock ordinal; `findRun` also accepts the ordinal and
   falls back to the newest finished Mock, so a hand-typed link always lands somewhere sensible.
5. The Mock does not touch the combo (S4: "Boss and Mock never touch the combo") and writes no `cards[id]`
   rarity — a Mock is a measurement, not a play. Only misses move the schedule.
6. `bumpCounters` covers the counters a Mock can honestly judge (`setups`, `rejects`, `bothRoots`, `twoCases`,
   `systems`, `signLead`, and `notationClean` up/reset). `forgeFlash` and `coldRecall` need per-part timing and
   review context the Mock does not have, so they stay Card-only.
7. Section E's SYS slot has no packet original (the doc has none), so it always generates from `T-sys`; its
   three registered modes are what make it a ≥ 3-source slot.
