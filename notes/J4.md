## 1. What was built

`site/js/job/crew.js` is the whole of G2's "Crew — capacity, not currency" and "The build decision,
with the numbers", plus G3.8's alignment theorem expressed as a function.

**Five things it owns.**

1. **Capacity.** `capacity = 8 + floor(xp.levelFor(save.xp)/2) + bossStamps`, clamped to 8…22. Boss
   stamps are the `trophies['boss:B1'…'boss:B7']` keys `data/trophies.js` already mints, capped at
   seven. Nothing the game itself writes enters this function — that is the anti-grind design.
2. **Allocation.** `allocate(save, make, rank)` is the only way a rank moves. It is **pure** (a new
   crew map and a new save; neither argument touched) and it is **closed under the invariant**: from
   any legal state, no sequence of calls can reach `spent > capacity` or `manned > min(capacity, 12)`.
   `legalize(save)` is the repair path for a save the rest of the app made illegal — principally G4's
   Mock miss, which drops a mastered make to 69 and therefore drops its HELD to STEADY.
3. **What a rank is worth on ONE target.** `forgivenessOf(save, make, target)` returns the number of
   rungs forgiven — which is exactly the `rank` argument `econ.rhoFor(rung, rank)` takes, because
   `ρ_eff = LADDER[max(0, rung − rank)]`. `isIdleFor` implements G12 #4's replacement rule: the crew
   stands down **only** on a target that is its own make's due review, never for a whole job.
   `holdsChain` implements HELD's chain-hold with both of its conditions (chain ≥ 3 **and** a
   non-clean outcome) and its suppression on due-review targets.
4. **The allocation gradient.** `crewValue(save, make, shape)` — a positive constant of the shape
   times `w · (1 − m/100)`, which is `readiness.skillState().score` to the bit. That identity is the
   alignment theorem, and `tests/job-align.test.mjs` is 21 tests about it.
5. **The measurement harness.** `bandFor` / `drawRung` / `encountersIn` / `simulateJob` — the pure,
   seeded machinery the suite runs G2's five matrix parameters through. J8 and J9 can reuse it.

### The one design decision that needed making: `Δρ̂(m)`

G3.8 asserts `Δρ(m_i) · encounters_i ∝ w_i(1 − m_i/100)`. The *true* `Δρ` read off the three shipped
bands is mildly concave in `(1 − m/100)` — 0.272, 0.268 and 0.213 of `Δρ` per unit of weakness at
m40 / m60 / m85 — so it is a proportionality, not an identity. `DRHO_SLOPE` is therefore a
**least-squares fit through the origin of the three shipped bands**, computed at module load from
`RUNG_BANDS` + `econ.expectedRho`, never typed in: 0.26908. A band that moves moves the slope.

`crewValue` evaluates `w * (1 - m/100)` as **one expression, in the same factor order as
`readiness.skillState`**, and only then scales it. That is load-bearing, not fussiness: ordering the
multiplication differently splits exact ties (`CS-RATIO` at m60 against `CS-QUAD` at m50 are exactly
tied at 2.0) by a last-bit rounding, and Spearman ρ comes apart at precisely the cases the theorem is
most interesting on. The first draft of this file did that and `job-align` caught it.

## 2. Exported API — exact signatures


### Allocation

```js
canAllocate(save, make, rank, opts?):
  { ok, reason: string|null, from, to, manned, spent, capacity, mannedMax }

allocate(save, make, rank, opts?):
  { ok, reason, make, from, rank, changed, crew, save,
    capacity, mannedMax, manned, spent, free, slots, legal }

legalize(save, { shape? }?):
  { crew, save, changes: Array<{make, from, to, reason}>, ...budget }
```

`allocate` refuses in this order: unknown make → bad rank → **HELD without `isMastered`** → (any move
that does not RAISE the rank is accepted here, so a reduction is never refused) → the manned cap →
capacity. A refusal returns the save **unchanged**; it never throws and never silently clamps.

```js
forgivenessOf(save, make, target = null): 0|1|2

```

```js
    constant, value, rank, mastered }

```

### The 4×2 matrix

```js
matrixParamsFor(shape, over?): Params        // `over` prices it with MEASURED parameters
steadyPerPoint(p): number                    // Δρ_steady · L̄ · m̄ · e_forgiven / 1
heldPerPoint(p): number                      // [Δρ_held · L̄ · m̄ · e_held + h·V_hold] / 2
buildRowFor(shape, over?):
  { shape, params, steady, held, h, vHold, heldForgiveness, heldChainHold, winner, margin }
buildMatrix(over?): Row[]
bestRankFor(shape, over?): 'STEADY' | 'HELD'
```

### The measurement harness

```js
bandFor(m): number[5]                        // interpolated between RUNG_BANDS, sums to 1
drawRung(band, u): 0|1|2|3|4                 // inverse CDF; `u` from a SEEDED rng
encountersIn(queue, make): { total, idle, active, byRole }
simulateJob(queue, { rng, crewRank?, m?, bag? }):
  { rows: [{i, chain, mult, rung}], rungs, holds, mSaved, mBar, chain3, pChain3 }
mean(xs): number
relErr(measured, published): number
```

`simulateJob` accepts an `rng.mulberry32` Rng object **or** a bare `() => number`. It runs the chain
under J1's own `chainAfterTarget` and bags under J1's own `pushOrBag` threshold; `mSaved` is computed
against a shadow continuation that replays the same rungs from a reset chain.

## 5. The measurement, and the objections

G2 instructs this explicitly: *"Every parameter in that table is a measurement, not a guess, and J4
owns the measurement … If a measured parameter moves the winner of a row, the row in this document is
wrong and the ticket updates it — the flip structure below is the claim, not the decimals."* So: the
spec's formulas are implemented exactly, the measurement is reported unbent, and the objection is
here rather than in a softened number.

### 5.1 The table

Population: 1 000 seeded saves (`mulberry32`, no `Math.random`), each composed by the real
`composePage`, restricted per row to saves where the row's decision is **live** — `capacity ≥ 10`,
and for the HELD column ≥ 3 mastered makes. Queue: the shape's target count drawn evenly from the
composed page with the shape's own tier mix. Crew **follows supply** (the marginal point is bought on
the make with the most non-idle targets on the board — what "per point" prices). Rungs from the
make's interpolated band; chain under `econ.chainAfterTarget`; bagging under `econ.pushOrBag`.
2 500 jobs per shape = **10 000 jobs**.

|---|---|---|---|---|---|
| RUN | **1.277** (1.3, −1.7 %) | 1.039 (0.9, **+15.5 %**) | 0.304 (3.6, −91.6 %) | 0.220 (0.12, +83.6 %) | 0.216 (1.2, −82.0 %) |
| JOB-10 | **1.417** (1.4, +1.2 %) | **1.604** (1.4, +14.5 %) | 0.453 (5.0, −90.9 %) | 0.340 (0.42, −19.0 %) | 1.554 (3.0, −48.2 %) |
| JOB-12 | **1.448** (1.5, −3.5 %) | 1.316 (1.7, −22.6 %) | 0.538 (5.6, −90.4 %) | 0.358 (0.50, −28.3 %) | 1.373 (3.4, −59.6 %) |

Every one of these 20 numbers is asserted twice: as a **regression pin** at ±2 % of the measured value
(so any drift in `composePage`, the ladder, the bag threshold or the population fails a test), and as
a **bounded deviation** from G2 in the direction the measurement actually went. Neither assertion is
vacuous and neither bends a number.

### 5.2 `e_held` is the one that matters, and it is structural

`e_held = 5.0` on a JOB-10 means half of a ten-target job is the **same make**. Measured on a flat
`composePage` queue, the best-supplied make of all nineteen reaches a mean of **1.56** non-idle
targets and **2.98** counting its own due reviews — so 5.0 is out of reach by construction, not by a
sampling accident. The suite asserts that ceiling directly.

The consequence is the objection: **priced with the measured parameters, HELD loses every row.** The
JOB-10 row needs `e_held ≥ 6.70` (holding every other parameter at its measured value) for HELD to
win; the board supplies **0.45**. 6.70 is inside a ten-target job, so the flip structure is not
impossible in principle — but it asks for two thirds of a job to be the one crewed make. Both numbers
are asserted.

The three smaller misses have plainer causes and I would not move the document for them:
`P(chain ≥ 3)` is high on the RUN and low on the three longer shapes because J1's `pushOrBag`
threshold banks (and therefore resets the chain) more often on a rich board than G2's estimate
assumed; `Σm_saved` is low because holds are rare when the chain rarely reaches 3, and the two errors
compound; VAULT `m̄` is low for the same reason (7 targets, hard tiers, short chains).

### 5.3 What `composeBundles` did to the picture — the Cold Crew result

J5 landed `composeBundles` / `draftUnion` while this ticket was running, so the acceptance's
"`composePage` + `composeBundles`" became measurable and the suite measures it (§9.4). The result is
sharper than the flat-page one and is, I think, the most important thing this ticket found:

| path | drafted length | share of targets that are due reviews | `e_forgiven` | `e_held` |
|---|---|---|---|---|
| flat `composePage`, JOB-10 | 10.0 | 71 % | 1.60 | 0.45 |
| **`composeBundles` + `draftUnion`, JOB-10** | 10.0 | **100 %** | **0.000** | **0.000** |
| the same, on a *keeps-up* control population | 10.2 | **86 %** | 0.628 | 0.026 |

`composeBundles` reshapes the page to the shape's budget and puts the **criticals** first, which is
correct and is G3.7 proof 7. But a critical is a due review, and G12 #4's idle rule stands the crew
down on every target that is its own make's due review. Put together: **on a board made of the
student's own dues, the crew is idle on essentially every target, and both crew ranks pay zero.**

This is not a bug in J5 and not a bug in the idle rule — it is G1's own **Cold crew** failure state
(`4 crew idle on their own reviews · 9 dues · clear them first — 4 minutes`) turning out to be the
*normal* case rather than an edge case. The control population (a student who keeps up, only 22 % of
cleared cards overdue) still spends 86 % of a drafted JOB-10 on due reviews.

**My objection, for the murder board, not acted on here:** either the idle rule or the critical-first
partition needs to give. Three options, in the order I would rank them:

1. **Idle only the make's *most overdue* due review in a job**, not all of them. Keeps the honest
   part ("a review is answered bare") and keeps HELD's gate meaningful, but stops a due-heavy board
   from zeroing the mechanic. One-line change to `isIdleFor`, and the rule stays per-target.
2. **Let the crew forgive on a due review but suppress only the chain-hold** there. Preserves G2's
   sentence about the chain-hold verbatim and gives STEADY something to do on a review board.
3. Leave it, and accept that crew is a mechanic for the second half of the unit, when the dues thin
   out. Defensible — but then G2's `e_held = 5.0` and the whole HELD column are wrong, and the board
   should say so.

I implemented the spec as written (option 3's behaviour) and did not touch the rule.

## 6. Open issues

1. **`e_held` and the HELD column (§5.2, §5.3).** The spec's number is unreachable from the composer
   as it stands. The suite asserts the measured value and the ceiling; the matrix still reproduces
   G2's published cells from G2's published parameters, so §8's acceptance is met on the published
   table and fails on the measured one. Someone has to pick a resolution — see §5.3.
2. **`dRhoSteady()` is 0.1635, G2 prints +0.163.** G2's `E[ρ]` table is printed to 3 dp (0.5615 and
   0.7255 are the real values), so the published `Δρ` is a rounded subtraction of rounded numbers.
   Tolerances in the suite are 0.0015, and the note records it rather than rounding the constant.
3. **`Δρ̂(m)` is a linear model, and the true `Δρ` is mildly concave.** G3.8 asserts a
   proportionality; §1 above says exactly what fit is used and why. Any strictly-increasing model
   that is a positive multiple of `(1 − m/100)` preserves ρ = 1; a *concave* one would not, and would
   break the theorem, so the linear fit is the one the theorem needs.
4. **`crewValue` does not read `q̂`.** The `q̂ ≥ 0.5` restriction belongs to G3.8's *third* row (the
   rating weight `4q̂(1−q̂)`), not to the crew gradient, which is monotone on the whole of [0, 1]. The
   align suite asserts both facts, and the restriction is asserted with a worked counterexample and a
   398-of-400 population result. `job-align` uses the documented link `q̂ = m/100` for the ordering
   argument and grounds it once against the real `call.qHatFor` on constructed card histories.
5. **`legalize` is not wired to anything yet.** It is the function J6/J7/J11 need when the Mock drops
   a mastered skill to 69 (G4's `FAC2 crew HELD → STEADY — the Mock says it is not held.`). Until it
   is called, `effectiveRankOf` already refuses to *pay* a lapsed HELD, so the ladder is correct even
   on an un-repaired save — but the save will still print `HELD` on the crew grid.
6. **Boss stamps are counted off `trophies['boss:<id>']`.** If J11 or a later ticket introduces a
   separate stamp store, `bossStampsOf` needs to read it instead.
