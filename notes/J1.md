## 5. Deviations and objections (the spec was implemented; these are recorded, not fixed)

### 5.1 One published numeral does not reproduce: G3.2's deep table, (chain 2, call 85)

`θ* = m·P/(ρ̄·W·(m−1))` at `m = 1.4`, `W = 1.8`, `P = 2.0`, `ρ̄ = 1` gives `θ* = 2.8/0.72 =
3.888888…`, so `q* = θ*/(1+θ*) = 0.7954545454545455` → **0.795** at 3 dp. G3.2 prints **0.796**.
Where 0.796 came from: rounding `θ*` to 3 significant figures first — `3.89/4.89 = 0.79550…` → 0.796.
Per BUILD-POLICY and the ticket's own instruction the FORMULA is the authority, so:

- `PUBLISHED.deepQ[2][85] = 0.795` (asserted), and
- `PUBLISHED.deepQAsPrinted = { 2: { 85: 0.796 } }` keeps the printed numeral on record, with the
  intermediate-rounding explanation asserted alongside it.

**Request to whoever next edits COMPOSED-GAME.md: change G3.2's table cell from 0.796 to 0.795.**
Every other cell in that table reproduces exactly.

### 5.2 `Δρ` for STEADY on an m40 make: 0.163 is a difference of ROUNDED values

Raw `E[ρ]` at m40 is `0.5615` (r0) and `0.725` (r1); the raw difference is `0.1635`, which rounds to
0.164, while G2 prints **+0.163** — the difference of the rounded table values (0.725 − 0.562). The
suite asserts the difference-of-rounded form, which is what the document's own table supports. The
other two Δρ figures are exact either way: HELD on m85 is `0.9885 − 0.9395 = 0.049`, and mastery is
`0.9395 − 0.5615 = 0.378`. No objection — just naming which arithmetic produces the printed numeral.

### 5.3 The `w·E[c]` peak/band is the CONTINUOUS object; the sanity table is the DISCRETE one

G3.1 point 2 derives the peak and band from `4q̂(1−q̂)·(10 − 40q̂(1−q̂))` explicitly, so
`stakePeak()`/`stakeBand()` default to that object and produce the published 0.854 and
[0.763, 0.925]. The G3.1 "Sanity" table is computed on the four-rung ladder instead (2.240 at
q̂ = 0.80, not the continuous 2.304), so `wTimesEcDiscrete` ships beside it and the suite asserts
both without "correcting" either. Recorded for the record, not asserted as a published value: the
discrete object's own peak is `q̂ = 0.8528432833`, value `2.4997974068`, band
`[0.7785731100, 0.9248729907]`.

Both objects are symmetric about `q̂ = 0.5`, so the search is restricted to `STAKE_DOMAIN = [0.5, 1]`
— which is G3.8's own explicit domain restriction ("`4q̂(1−q̂)` is strictly decreasing on
`q̂ ∈ [0.5, 1]`, which is where every target the composer serves as a *stake* lives"). Without that
restriction a naive grid search returns the mirror peak at `q̂ = 0.146` and a mirror band starting at
0.075. **J2 and J7 must apply the same restriction wherever they print or search this curve.**

A precision note: a smooth maximum is flat to second order, so the located `q̂` is accurate to about
1e-8 rather than 1e-15 — four orders of magnitude finer than the 3 dp the document prints. The suite
asserts `r3(qHat) === 0.854` and a 1e-6 tolerance against the closed form.

### 5.4 `honestRung(0.900)` is an exact tie, resolved to the lower rung

At `q̂ = 0.900` — the published 85↔95 rating indifference point — both rungs score `E[c] = 6.3`, so
`w·E[c] = 2.268` either way and the published sanity row is unaffected. `honestRung` breaks exact
ties to the LOWER rung; the switch to 95 happens one 1/1000 step later. Same at 0.600 and 0.775.
**J2's `argmaxCall` should break ties the same way** (the carry ladder has the same three ties) so the
debrief's two regret lines never disagree about the boundary.

### 5.5 `bagFee` / `bagBank` are defined so the printed line adds up

G2 says `BAGGED += 0.9·LOOSE` and `fee = 0.10`. LOOSE is an integer (every `Δloose` is rounded), so
`0.9·LOOSE` can be a half. The line the app prints is `bag 131 (fee 13 · chain 4 → 0)` →
`bagged 118`, i.e. the fee and the bank must sum to LOOSE exactly. So `bagFee(s) = round(0.10·s)` and
`bagBank(s) = round(s) − bagFee(s)`. Asserted for every `s ∈ [0, 400]`: `fee + bank === s`, and
`|bank − 0.9·s| ≤ 0.5`. On half-unit piles (e.g. `s = 105`) this banks 94 where a literal
`round(0.9·s)` would bank 95 — a ≤ 1-loot difference, always in the house's favour by less than one
loot, and `bagBankExact()` exposes the unrounded value for anyone who wants it.

### 5.6 The ×2 posting is a factor in BOTH branches, though G2's formula lines omit it

G2's `clear:` and `miss:` lines do not mention the ×2, but G3.6 defines it as a posting multiplier and
G3.7 proof 1 requires that "the guard and the ×2 multiply both the clear and the miss branch
identically". So `x2` is a factor in `carryFor`, `missFor` and `postedFor`, defaulting to off.
The guard's own terms stay asymmetric exactly as published (`wing` on the clear branch,
`wing_pen = 2` on the miss branch) — that asymmetry is the spec's, not an implementation choice.

### 5.7 G1's illustrative "first 90 seconds" block does not reproduce from the formula

The walkthrough prints `posted 11` for a VOC tier-1 review at cold 3 d and then `+24 loose` on a clean
95 call. `11 × 2.2 = 24.2 → 24`, so the printed payout is consistent with `round(posted) × W` — but
the target also carries `RECALL 2 (×1.50)` tokens in that same block, and with the wing term the
posted value would be `6 × 1.25 × 1.5 × 1.5 = 16.875 → 17`, not 11. The narrative block is
illustrative and the formula is the authority, so `carryFor` does ONE round of the whole product
(`L · ρ_eff · m_chain · W · scope · wing · cold · tell · ×2`) exactly as G2 writes it, and `postedFor`
is the same product without `ρ_eff`, `m_chain` and `W`. **Consequence J6 must know: `posted × W` is
not always equal to the paid `Δloose`** (two roundings vs one). If the debrief needs them to agree to
the digit, say so and I will add a `postedThenMultiply` variant rather than have J6 invent one.

### 5.8 `FIXED_PHASES.RUN.full` has no per-phase split, because G1 never publishes one

G1's fixed-phase table publishes RUN's full-use total as **130 s** but only gives RUN's per-phase
numbers for the default path (`12 · 12 · 20 · 20 · 40 = 104`). The JOB column publishes both
(`18/12/20×2/25/65/0 = 160` and `55/12/50×2/25/65/25 = 282`). 130 − 104 = 26 s does not decompose
from anything the document states, so **nothing was invented**: `FIXED_PHASES.RUN.full.phases` is
`null` and `fixedSeconds('RUN', 'full')` returns the published total. Every other cell sums from its
phases and is asserted to equal the published total. **J8 owns the measurement that fills this in.**

### 5.9 VAULT is credited two brief windows but has only seven targets

`SHAPES.VAULT.briefs = 2` and `SHAPES.VAULT.fixed = 'JOB'`, which is forced: G1's shape table gives
VAULT `game s = 316 → 438`, and `316 − 156 = 160` / `438 − 156 = 282` is exactly the JOB fixed column,
which contains two 20 s (or 50 s) brief windows. But G1 also lands the windows "after targets 4 and 8",
and a VAULT has 7 targets, so the second window cannot fire where G1 places it. The split arithmetic
is the authority here, so the constant stays at 2 and the placement conflict is recorded.
**J6/J8: either the VAULT's second window lands after target 6, or the VAULT's fixed total is 20/50 s
lower than G1 prints. Pick one and write it down; do not let the two tickets pick differently.**

### 5.10 `RUNG_BANDS` r2 is computable for m60 and m40, and G2 marks it n/a

`expectedRho(RUNG_BANDS[60], 2) = 0.932` and `expectedRho(RUNG_BANDS[40], 2) = 0.8595` are perfectly
well-defined, but G2 prints `n/a` because HELD requires `mastery.isMastered` and neither band is a
mastered make. `PUBLISHED.rhoTable[60].r2` and `[40].r2` are therefore `null` and the suite skips
them, asserting the gate (`CREW_RANKS[2].requires === 'mastery.isMastered'`) instead. **J4 enforces
the gate; `econ.rhoFor` deliberately does not — it is a pure ladder lookup and must stay one.**
